# ADR 0066 — Static descriptor templates and manifest externalization

**Date:** 2026-05-02
**Status:** Proposed
**Related:**
[ADR 0011 — Descriptor-first module v2](0011-descriptor-first-module-v2.md),
[ADR 0044 — Dynamic module loading and reload](0044-dynamic-module-loading-reload.md),
[ADR 0060 — Structural parameter flag and `ModuleShape` reduction](0060-structural-parameter-flag.md),
[ADR 0064 — Non-Rust FFI plugins](0064-non-rust-ffi-plugins.md)

## Context

After ADR 0060 reduces `ModuleShape` to `{ channels }`, descriptor
construction is still expressed as a **runtime function call**:

```rust
fn describe(shape: &ModuleShape) -> ModuleDescriptor;
```

Each `Registry::describe()` call invokes the per-module function, which
allocates port and parameter vectors, fills them via builder methods,
and returns the result. The descriptor's structural information is
implicit — computed by Rust code, not declared.

Two consequences ripple from this:

1. **LSP must link every module crate.** `default_registry()` calls
   `r.register::<T>()` for ~50 module types; each `register` invokes
   `T::describe()`. To call `describe()` LSP must depend on
   `patches-modules`, which transitively pulls in every module's
   dependencies (DSP kernels, FFT, file decoders, MIDI, …). A typical
   LSP request only needs port names, kinds, and parameter ranges —
   data that has no business being computed by linking and running
   audio-engine code.
2. **The FFI ABI re-derives descriptors per-instance.** The `describe`
   vtable entry takes `FfiModuleShape`, allocates inside the plugin,
   serializes to JSON, and returns owned bytes the host must free.
   The descriptor is recomputed for every instance even though, given
   `channels`, it is fully determined by the module type.

Descriptor structure is **static information about a module type**.
Treating it as runtime computation is incidental.

## Decision

### 1. `ModuleDescriptorTemplate` as the source of truth

Each module type owns a compile-time-constant `ModuleDescriptorTemplate`
that fully describes its descriptor shape, parameterized by channel
count.

```rust
pub struct ModuleDescriptorTemplate {
    pub name: &'static str,
    pub axes: &'static [CountAxis],
    pub global_inputs:      &'static [PortTemplate],
    pub per_axis_inputs:    &'static [(AxisId, PortTemplate)],
    pub global_outputs:     &'static [PortTemplate],
    pub per_axis_outputs:   &'static [(AxisId, PortTemplate)],
    pub realtime_params:    &'static [ParameterTemplate],
    pub structural_params:  &'static [ParameterTemplate],
    pub per_axis_realtime_params:   &'static [(AxisId, ParameterTemplate)],
    pub per_axis_structural_params: &'static [(AxisId, ParameterTemplate)],
}
```

`CountAxis` names a count dimension (today exactly one: `"channels"`).
The internal multi-axis representation is forward-looking insurance
against future shape dimensions (taps, voices, matrix dims). The DSL
surface and `build()` signature take only `channels: u32`.

```rust
impl ModuleDescriptorTemplate {
    pub fn build(&self, counts: &[(AxisId, u32)]) -> ModuleDescriptor;
    pub fn build_channels(&self, channels: u32) -> ModuleDescriptor; // convenience
}
```

The `Module` trait gains an associated const, and the existing
`describe(shape)` becomes a defaulted thin wrapper:

```rust
pub trait Module: 'static {
    const TEMPLATE: ModuleDescriptorTemplate;
    fn describe(shape: &ModuleShape) -> ModuleDescriptor {
        Self::TEMPLATE.build_channels(shape.channels as u32)
    }
    // ... rest unchanged
}
```

Modules migrate by replacing imperative descriptor builders with a
declarative `const TEMPLATE`. Once all modules are migrated, the
`describe` trait method is removed in favour of direct `TEMPLATE`
access.

### 2. ModuleManifest: descriptor info as data

`ModuleManifest` is a serializable, build-time-emittable bundle of
every module type's `ModuleDescriptorTemplate` plus version metadata.

```rust
pub struct ModuleManifest {
    pub schema_version: u32,
    pub generator: GeneratorInfo,
    pub modules: Vec<ModuleManifestEntry>,
}

pub struct ModuleManifestEntry {
    pub name: String,
    pub template: ModuleDescriptorTemplate, // owned, serializable mirror
}
```

Two mirrored types: `ModuleDescriptorTemplate` (static, `&'static str`,
in core) and an owned, serde-friendly twin used by the manifest. A
`From` impl converts between them.

The manifest is generated by extending the existing
`patches-tools/src/bin/patches-manifest.rs` binary with a `--json`
flag. The generator links module crates, walks the registry, and emits
the manifest. This is the **only** place that needs to link
`patches-modules` (besides the audio engine itself).

### 3. LSP consumes the manifest, not the registry

`patches-lsp` drops its `patches-modules` dependency. It loads
`ModuleManifest` at startup (path configured, with a baked-in default
manifest as fallback for the bundled binary). All sites that today
call `registry.describe(name, shape)` look up the manifest entry and
call `entry.template.build_channels(channels)`.

Because the manifest is data, third-party plugin manifests can be
merged at LSP startup without dynamic loading.

### 4. FFI: expose the template, not a describe function

The FFI vtable replaces the per-instance `describe(shape) -> bytes`
entry with a per-plugin `module_template() -> &'static [u8]` returning
a pointer to a serialized `ModuleDescriptorTemplate`. Hosts decode
once, build per-instance descriptors locally via `template.build_channels`.

Consequences:

- One serialized blob per module type, not per instance.
- Plugin SDK bundles a `module_template!` macro that emits the static
  blob from a Rust `ModuleDescriptorTemplate` at compile time.
- Plugin manifests can be aggregated into the LSP-consumed
  `ModuleManifest` by walking installed plugins offline — no dlopen.

ABI version bumps to 8.

## Consequences

### Positive

- LSP no longer links module crates. Compile time and binary size both
  drop substantially. Transitively unblocks the ABI externalization
  roadmap: anything that consumes module *shape* (LSP, SVG renderer,
  drum sequencer UI, future GUIs) can do so without linking the audio
  engine.
- Descriptor info is data. Tools (doc generators, type checkers,
  property tests over module surfaces) consume the manifest instead of
  reimplementing `default_registry()`.
- FFI plugins describe themselves once, not per instance. Allocation
  and JSON encoding leave the per-instance hot path.
- Forward-compatible with multi-axis shapes (matrix mixers, multi-tap
  delays with independent counts) without another ABI break.

### Negative

- Two parallel template types (`&'static` for in-tree modules,
  owned/serde for the manifest). Trivial mirror, but doubled types
  must stay in sync. Mitigated by a single source-generation strategy
  (manually-paired in `patches-core`, with a derive macro if it grows).
- `ModuleDescriptorTemplate` is intrinsically more verbose than the
  current builder chain for tiny modules (one `mono_in` + one
  `mono_out`). Acceptable: most modules have non-trivial port lists,
  and the const form reads better for them. The trivial cases stay
  short.
- Manifest staleness: a manifest generated for an older module set
  could be consumed by a newer LSP. Schema version + generator info
  catches incompatibility loudly; a CI step regenerates the bundled
  manifest when modules change.

  **Schema version bump policy.** `patches_manifest::SCHEMA_VERSION`
  starts at `1`. Bump on any change that breaks deserialization of
  older manifests by a newer consumer, or vice versa: adding a
  required field, removing a field, renaming a field/variant, or
  changing the encoding of a variant. Adding a new optional field
  (with a serde default) does not require a bump. Adding a new
  `OwnedParamKind` variant requires a bump iff older consumers must
  reject manifests using it; if forward-compatibility via
  `#[serde(other)]` is acceptable, treat as additive. Consumers
  compare on equality and refuse mismatched manifests with a clear
  error pointing at the regeneration command.
- ABI bump (7 → 8). All existing FFI plugins rebuild. Acceptable —
  this lands alongside ADR 0060's bump and should be combined into a
  single break.

### Migration

1. Land `ModuleDescriptorTemplate` types and the manifest mirror in
   `patches-core`. Add `Module::TEMPLATE` with a defaulted
   `describe()` body, allowing modules to migrate one at a time.
2. Migrate modules in batches (single-channel; channel-aware;
   poly-fixed). Each module's old `describe()` body is deleted in
   favour of a `const TEMPLATE`.
3. Remove the `describe()` trait method once all modules have migrated.
4. Extend `patches-manifest` CLI with `--json`. Wire CI to regenerate
   the bundled manifest on module changes.
5. LSP: load the manifest at startup, replace `registry.describe()`
   call sites with manifest lookups, drop `patches-modules` from
   `Cargo.toml`.
6. FFI: bump ABI to 8, replace `describe` vtable with
   `module_template`, update `export_plugin!` macro and test plugins.

Sequencing: ABI 0060 (structural params) and 0066 (templates) ship in
the same ABI break to avoid two consecutive bumps.

## Non-goals

- Descriptor caching or memoization in the host. The build cost is
  a few vector copies; not worth complicating.
- Deriving `TEMPLATE` via proc macro at this stage. Hand-written is
  fine for ~50 modules; a macro is a follow-up if it pays off.
- Multi-axis DSL surface. The internal `axes` mechanism is in place
  but the DSL stays single-int-or-alias-list (per ADR 0060 §Migration).
